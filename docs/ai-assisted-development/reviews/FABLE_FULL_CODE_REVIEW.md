# Big Screen Independent Engineering Audit

Reviewer: Fable (Claude), acting as an independent third-party senior engineering reviewer.
This report is intended to be handed to Codex for finding-by-finding evaluation. Every finding below was personally verified by the lead reviewer against the source at the recorded commit; agent/subagent output was used only to locate candidates, and several agent candidates were rejected during lead verification (Section 22).

## 1. Executive Summary

Big Screen at commit `6cbf791` is, by a wide margin, better engineered than a typical alpha Quest mod. The core playback path — `FrameDecoder`, `FrameDecoderFacade`, `PlaybackSession`, and the hook layer in `main.cpp` — is genuinely excellent: condition-variable predicates are held under the correct mutexes, worker shutdown is signal→join→free with a bounded-time Unity-thread budget and a background retirement reaper, stale output is rejected by decode epochs and presentation generations, Beat Saber's song clock is the sole playback clock, and the FFmpeg 4.4/9 dual-backend isolation is enforced by an ELF audit at package time. Ownership and cleanup discipline in the rendering layer is similarly strong (explicit `ownsTexture_`, clones-destroyed-before-owner, rollback-on-failure geometry swaps, pervasive `UnityW::isAlive` checks). Comments are unusually good: they document invariants, threading contracts, and the *reasons* for workarounds, and spot-checks found them overwhelmingly accurate.

The defects that do exist cluster at the edges rather than the core: two High-severity items (a stale `.part` file that can be resumed into a *different* format or URL, and an error-classification mistake that lets an ordinary disk-full condition eject the user from the menu and then disable the whole mod), a set of Medium items (a UI cache invalidation that degrades the video browser after every save, an unreachable ~90-line downloader rollback path, a log-redaction gap, two narrow state-commit-ordering gaps in `ScreenSurface`, per-frame GC churn in the GPU upload path, and Windows/Linux deployment-tooling parity drift in exactly the ownership-safety logic the project is most proud of), and a longer tail of Low polish items. The most significant AI-era symptom is not fragility but *accretion*: `VideoLibraryMenu.cpp` (6,256 lines) and `DownloadManager.cpp` (4,936 lines) have absorbed too many unrelated jobs, the same state (`terminalDownloadProgressLevelId_`) is defensively cleared at 64 call sites, and the repository-invariant test suite has grown to ~1,500 verbatim source-text assertions that tax every refactor.

One high-consequence question could not be settled statically and must be verified on-device before beta: whether multiplayer/tutorial gameplay (whose scene-transition types are not hooked) can start a stale solo-prepared video (Section 8).

Verdict (Section 25): **READY FOR FIRST-ROUND BETA AFTER THE LISTED BLOCKERS.**

## 3. Overall Engineering Assessment

The codebase has one recognizable engineering philosophy and mostly holds to it: a single main-thread owner (`PlaybackSession`) driven by public Beat Saber lifecycle hooks, background work confined to mailbox-pattern workers that never touch Unity/IL2CPP objects, transactional replacement for anything persistent (library manifest with validation + rotated verified backups + quarantine, staged file replacement for downloads, receipt-driven deployment with baselines), errors split into an explicitly documented taxonomy (`RecordError` for expected failures vs `ReportInternal` feeding a circuit breaker, with dialogs deferred past gameplay), and pinned-by-hash external inputs everywhere in the build. The document `docs/ARCHITECTURE.md` matches the real module structure down to obscure constants, which is rare.

Where the standard slips, it slips in recognizable ways: guard-style drift inside one file (raw-pointer checks in `ApplyPresentation` versus the `isAlive` discipline its own `Upload` comment mandates), a mutate-then-commit ordering slip in `ShowLeadIn`, one error-severity misclassification that contradicts the codebase's own documented taxonomy, duplicated UI flows that have drifted apart, and two god-files that keep absorbing features. None of this looks like careless code; it looks like a large, fast-moving, mostly-AI-implemented codebase whose review gates caught the big things and let seams accumulate.

## 5. High-Severity Findings

### H-1 — A cancelled download's `.part` file is resumed into a different format/URL

```text
ID:        BS-H1
Severity:  High
Confidence: Medium-High
Category:  CONFIRMED DEFECT
Files:     src/DownloadManager.cpp; src/VideoLibrary.cpp; src/SelectionVideoToggle.cpp
Function/class: DownloadManager::Start, embedded DownloaderScript, VideoLibrary::AllocateVideoPath
Lines:     DownloadManager.cpp 2384–2386 (Start cleans only cancelPath/statusPath/diagnosticPath), 823–824 ('continuedl': True, 'nopart': False), 916–917 (outtmpl = job['finalPath'], format per request); VideoLibrary.cpp 909–926 (path = <FNV(levelId)>-{user|mapper}.{mp4|webm}); DownloaderScript line 672 ("Download paused. Select Resume to continue it."); SelectionVideoToggle.cpp 1216–1232 (cancelled state reopens the resolution dialog offering all tiers)
```

What is wrong: `Start()` deletes the previous operation's control files but never the staging media file or its `.part` sibling. The Python side deliberately resumes partials (`continuedl: True`), and the staging path is derived only from level + origin + extension — 480p/720p/1080p requests all share the same `…-user.mp4` path, and the same path is reused when the source URL for the map has changed. yt-dlp's resume issues a Range request at the existing byte offset with no cross-format validation.

Why it can really happen / trigger path: cancel a 1080p download partway (the UI itself says "Select Resume to continue it", so keeping the `.part` is intentional for the same-tier case) → press Download again → `selectedTransferNeedsAttention` reopens the resolution dialog → pick 720p (or the mapper updated the URL in the interim) → yt-dlp appends 720p bytes at the 1080p partial's offset.

Actual consequence: a spliced file. Because selected formats are video-only DASH, the subsequent remux/validation in `VideoContainerNormalizer` usually fails mid-file, triggering the alternate-transport fallback (which does clean the partial, DownloadManager.cpp 3307–3311) — so the common cost is a fully wasted transfer plus a confusing `BS-DL-PREP-FALLBACK-001` failure. Worst case, a spliced file whose head decodes passes the head-only probe (`CanDecodeSoftwareFrame`, ~600 packets) and is published to the library.

Existing protections examined and why insufficient: the 403-retry deletes the `.part` (937) but only within a single attempt; `runFallbackDownload` cleans it but only on the container-fallback path; `overwrites: True` affects the final file, not the partial; StorageManager only offers stale `.part` files older than 1 h as user-selectable cleanup.

Smallest sensible correction: persist a small sidecar `{url, requestedHeight}` next to the `.part` (or in the receipt/status file) and have `Start()` delete the incoming file and `.part` unless both match the new request. Regression tests: a `DownloaderScriptTests.py` case asserting `Start`-equivalent cleanup semantics for (same tier, different tier, different URL) partial files.

### H-2 — Disk-full while saving library.json is classified as an internal error: forced menu ejection, and two saves within 3 minutes disable the whole mod

```text
ID:        BS-H2
Severity:  High
Confidence: High
Category:  CONFIRMED DEFECT
Files:     src/VideoLibraryMenu.cpp; src/LocalVideoBrowserMenu.cpp; src/VideoLibrary.cpp; src/ErrorManager.cpp/.hpp; src/Settings.cpp (contrast)
Function/class: VideoLibraryMenu::SaveTiming (catch blocks), VideoLibraryMenu::RemoveOverride, LocalVideoBrowserMenu::SetSelectedVideo, ErrorManager::ReportInternal
Lines:     VideoLibrary.cpp 1802/1809/1841 (SaveLocked throws std::runtime_error on any write/validation failure — including storage-full); VideoLibraryMenu.cpp 4227–4254 (catch → ReportInternal("saving video timing")); ErrorManager.cpp 405–445 (ReportInternal → menuExitRequested_ outside gameplay; two internal errors within 3 minutes → circuit breaker), 633 (SetModEnabled(false)); ErrorManager.hpp 30–31 (RecordError is documented as the path for "expected or handled failure that does not need to count toward the internal-error circuit breaker"); Settings.cpp 1282–1295 (the equivalent settings-file write failure correctly uses ReportUserVisible only)
```

What is wrong: a full disk is the single most likely environmental failure for a video-download mod (the UI even displays Free Space), and `SaveTiming` already handles it gracefully — restores persisted values, publishes an editor notice, shows a user-visible dialog. The *additional* `ReportInternal` call is what escalates: one occurrence force-dismisses the entire Big Screen flow mid-edit; a second within three minutes (trivially produced by adjusting another slider) trips the breaker and the mod turns itself off with the "Big Screen disabled itself" dialog. This directly contradicts the codebase's own error taxonomy, and the sibling implementation for settings writes demonstrates the intended pattern.

Trigger path: fill the Quest with downloads → open the timing editor → adjust Playback Speed or Offset twice within three minutes.

Smallest sensible correction: in the `SaveLocked`-failure catch blocks (`SaveTiming`, `RemoveOverride`, `LocalVideoBrowserMenu::SetSelectedVideo`), replace `ReportInternal` with `RecordError` + the existing `ReportUserVisible`, or make `SaveLocked` throw a distinct I/O-failure type that callers route to the non-breaker path. Regression test: a host-side test that simulates a failing manifest write and asserts no circuit-breaker state change.

## 6. Medium-Severity Findings

Each finding below was verified at the cited lines by the lead reviewer. The Section 48 evidence fields are compressed for readability; "trigger" and "consequence" are stated inline.

### M-1 — Every library save wipes the browser's row-status cache with no re-warm path
`VideoLibrary::SaveLocked` (VideoLibrary.cpp 1731) clears the whole `descriptorCache_` on every persist. The song browser builds row subtitles, thumbnails, the JSON-issues button, and the "Maps With Video" filter exclusively from `CachedRowStatus` (VideoLibraryMenu.cpp 2705–2716), and the only bulk re-population, `PrewarmCatalogStep`, early-returns unless `catalogRefreshRequested_` is set (2559–2561) — which no save path sets. Trigger: change any timing value or pick a thumbnail, then return to the song list. Consequence: every row except the just-edited one degrades to "Checking video metadata", thumbnails vanish, and the Video filter goes empty until a SongCore refresh or menu re-entry. The targeted invalidation mechanism already exists (`RefreshMapperMetadata` erases a single `levelId`, VideoLibrary.cpp 897). Fix: pass the touched `levelId` into `SaveLocked` (all callers know it) and erase only that entry. Confidence: High (code path); Medium-High that the visual degradation is exactly as described (on-device confirm recommended). Test: host-side cache test asserting per-level invalidation.

### M-2 — The in-`Run()` yt-dlp rollback-and-retry block is unreachable for its stated purpose
DownloadManager.cpp 3179–3270 restores `yt-dlp-previous` and reruns the job when `PyRun_String` returns NULL, justified by an in-code comment about Python execution/import failures. But the embedded script wraps *everything involving yt-dlp* — including `import yt_dlp` (815–816) — in `try: … except BaseException:` (810, 1005–1022) that always publishes a terminal status, so a broken/corrupted package can never surface as `!result`. The only reachable NULL-result paths are pre-`try` stdlib imports, `json.loads` of C++-built JSON, or status-file I/O failure — none fixable by package rollback. (The real defense against a broken package, the startup smoke test at 2027–2178, works.) Secondary defects inside the dead path: the retry runs `DownloaderScript` *without* `MediaScriptHelpers` (3246–3250 vs 3171–3172), surviving only because `clean_error`/`is_sdr`/`tier` persist in the reused globals dict. Fix: delete the rollback/retry (keep the plain failure report), or key rollback off a distinctive published `errorCode` instead of interpreter failure. Confidence: High. This is the clearest patch-on-patch artifact in the repository.

### M-3 — Downloader exception diagnostics reach the persistent error log unredacted
Two sanitizers coexist: `sanitize_ytdlp_message` (DownloadManager.cpp 591–597) redacts authorization/cookie/PO-token values and URL query strings for logger output, while `clean_error` (566–567) only strips ANSI codes and truncates. Failure diagnostics are built with `clean_error` (1015–1022) and persisted verbatim by `ErrorManager::RecordError` into `error-history.log` (ErrorManager.cpp 297–309) — the file the support-bundle collector ships. yt-dlp exception texts routinely embed full signed `googlevideo` URLs. The C++ comment at 3451–3453 even claims the persisted failure is "sanitized", which it is not. Fix: apply the same redaction regexes in `clean_error` (or centrally in `RecordError`). Confidence: Medium-High. Test: extend `DownloaderScriptTests.py` to assert redaction of a synthetic signed-URL exception.

### M-4 — `ShowLeadIn(true)` mutates the video material before committing lead-in state; an early return strands a black picture
ScreenSurface.cpp 2409–2464: the black-lead-in path rebinds `material_` to the shared white texture with black tint (2435–2445) and only *afterwards* attempts `ConfigureNonEmissiveBackground` (2449–2451), returning early on failure without setting `leadInActive_`/`leadInBlack_` (2461–2462). `Upload` restores real presentation only when `leadInActive_` is set (2107–2118). `ConfigureNonEmissiveBackground` fails exactly when `FindVideoShader()` transiently fails — a condition the file itself documents and throttles (1-second retry). Consequence: if the transient failure coincides with the lead-in window, every subsequent upload writes into `texture_` while the material samples the black-tinted white texture — a silent, potentially song-length black screen. Fix: commit the state flags (or perform the mutation) only after all fallible steps succeed. Confidence: logic High; reachability Medium-Low (listed here because the failure is silent and full-length).

### M-5 — `ApplyPresentation`/`SetOpacity` use raw-pointer guards in exactly the window where `Upload` mandates `isAlive`
ScreenSurface.cpp 1747–1753 guards with `!gameObject_ || !material_ || …` while `Upload` (2088–2102) uses `UnityW::isAlive` with an explicit comment that after a level restart "a raw Texture2D pointer can remain non-null while referring to an already-destroyed object" and that calling through it can crash UnityMain. `SetOpacity` (2499–2512) has the same raw guard and funnels into `ApplyPresentation`; `PlaybackSession::Tick` calls `SetOpacity` every tick during the Cinema end fade (PlaybackSession.cpp 1372–1382) *before* `Upload`'s `isAlive` gate runs. The reachable windows are narrow (restart and finish paths are hooked and call `Stop()` first), but the inconsistency contradicts the file's own documented invariant, and the failure mode ranges from repeated caught internal errors (feeding the H-2 circuit breaker) to a native fault in a GC race. Fix: one-line change to `isAlive` guards in `ApplyPresentation` (and align `SetWorldTransform`/`SetWorldScale`/`SetVideoLocalRoll`, 2479–2497). Confidence: High on the inconsistency; Medium on reachability.

### M-6 — Timing sliders persist the full manifest and restart the preview decoder on every callback
The Video Playback Offset slider callback (VideoLibraryMenu.cpp 1753–1779) runs `SaveTiming()` — full JSON serialization of every level record, validation re-parse, backup rotation, remove+rename on flash, plus the M-1 cache wipe — *and* `StartSelectedPreview()` (full decoder Stop/Open/Start) *and* `RefreshDetails()` per callback. The repository's own comment (Settings.cpp 1066–1068) states BSML slider callbacks "may arrive dozens of times per second" and debounces the equivalent settings churn at 400 ms; `ThumbnailPickerMenu` likewise coalesces scrubs. Consequence: main-thread stalls and flash write amplification during a drag. Fix: commit timing on settle (mirror `Settings::Save`) and defer `StartSelectedPreview` behind the same timer. Confidence: Medium-High.

### M-7 — "JSON ISSUES" summary re-parses the entire library synchronously on the UI thread
`ShowBrowserMapperMetadataIssues` (VideoLibraryMenu.cpp 3460–3493) calls `VideoLibrary::Describe` for every catalog entry in one click. After any save (M-1) the descriptor cache is empty, so this becomes a full Cinema-JSON + playlist parse of every installed map — the code's own measurement is "roughly 800 ms first-open burst … with 578 maps" (comment at 2604), the very stall the incremental prewarmer exists to avoid. Fix: build the summary from cached row statuses / an issue list captured during prewarm. Confidence: Medium-High.

### M-8 — Linux deployment tooling skips the ownership-safety assertions and baseline restoration that the PowerShell path enforces
Two verified divergences in safety-sensitive tooling. (a) `scripts/copy.ps1` gates redeploys with `Assert-BigScreenPartialRecoverable` / `Assert-BigScreenManagedReceiptSafe` (235/239) and refuses when an on-device source-exclusive file's hash matches neither payload, pre-deploy state, nor baseline; `scripts/quest_tool.py deploy()` (≈494–560) has no equivalent and pushes unconditionally after classification. (b) For version-upgrade "retired" paths, PowerShell's `Remove-BigScreenRetiredReceiptFiles` refuses on hash mismatch and *restores the recorded baseline* when `previousState` was `present`; the Python deploy reuses the deliberately lenient uninstall policy (`receipt_removal_action` — hashes are intentionally not an uninstall gate, which is fine and documented *for uninstall*) and therefore `rm -f`s any present exclusive retired path regardless of hash and never restores baselines (quest_tool.py 482–491, 529–535). Bonus defect: the raised message "Retired source paths changed externally and were preserved" actually fires only when `rm` *failed* — the wording does not match its condition. Consequence: on Linux, an externally modified or baseline-shadowing file is silently clobbered/deleted during a routine update where Windows would refuse or restore. Fix: port the two assertions and a strict retirement routine into `deploy()`; fix the message. Confidence: High. (Also Low sibling: `MIXED_OR_AMBIGUOUS` removal — PS performs partial removal, Python refuses; align or document.)

### M-9 — Packaged-library list is maintained in three places with no cross-check
`mod.template.json` `libraryFiles`, `build_pipeline.py` `REQUIRED_LIBRARIES` (80–96), and the CMake staging loops each list the ~15 shipped `.so`s; `package_qmod()` silently overwrites the qpm-generated manifest list with the Python constant (line 877), and neither `validate_manifest()` nor the 1,529-assert invariant suite compares them (grep: zero hits for a cross-check). Adding a library to the template or CMake without touching the Python constant ships a package missing it, discovered on-device. Fix: one assert in `validate_manifest()` that the sets are equal. Confidence: High.

### M-10 — Release workflow comment promises debug artifacts that are never uploaded
`.github/workflows/build-ndk.yml` 28–29 says tagged builds publish "the validated QMOD and native debug artifacts"; the release step uploads only the `.qmod` (101–102), and the artifact step uploads the *stripped* `./build/libbigscreen.so` while line 74–75 proves `./build/debug/` exists and then drops it. Tombstones from released builds therefore cannot be symbolized without a bit-identical rebuild — despite `ndk-stack.ps1`/`pull-tombstone.ps1` existing for exactly that purpose. Fix: upload `build/debug/` (or correct the comment). Related Low: the extracted `VERSION` output is dead and tag↔`qpm.json` version consistency is never checked (60–65; only `TAG` is consumed at 98), so a mis-tagged release ships a QMOD whose `mod.json` disagrees with the release label. Confidence: High.

### M-11 — Three PowerShell test suites are wired to nothing
`tests/DeterministicZipTests.ps1`, `tests/QuestDependencyCheckTests.ps1`, and `tests/SourceInstallOwnershipTests.ps1` are invoked by no workflow, launcher, or CMake target (the first is only *read as text* by the invariant suite, line 91). The scripts they test — 341/591 lines of Quest install/removal safety policy that touches users' headsets from `Build-And-Deploy.bat` — can rot silently, and given M-8 the ownership tests are precisely where coverage matters. `ubuntu-latest` ships `pwsh` and the suites are explicitly ADB-free pure-policy tests. Fix: add a CI `pwsh -File …` step or register them in `tests/CMakeLists.txt` behind `find_program(PWSH pwsh)`. Confidence: High.

### M-12 — Chroma map detection/preview parses multi-megabyte beatmap JSON on the Unity thread
`ChromaMapDetector::UsesChroma` parses every `.dat` in the level directory and walks the full JSON tree; it is fingerprint-cached (531–583), but `ApplyCinemaScreenPreview` (620–648) — re-run on every difficulty change via `PlaybackSession::ConfigurePreviewBeatmap` (258–271) — is uncached and parses the selected difficulty file (routinely 10–50 MB for large Chroma maps) synchronously on UnityMain. Consequence: several-hundred-ms menu hitches on video-enabled Chroma maps, repeated per difficulty click. Fix: cache preview results by (dir, characteristic, difficulty, fingerprint). Confidence: High on behavior, Medium on felt severity.

### M-13 — Raw `BeatmapLevel*` retained across SongCore refreshes; rebuild deferred while the editor is open
Category: REALISTIC RELIABILITY RISK. `SongLibraryItem::level` and `selected_` are bare IL2CPP pointers in native containers (VideoLibraryMenu.hpp 50, 332–335) — not GC-visible roots. The code knows SongCore replaces its level objects on refresh (ShowcaseLauncher.cpp 342–346 says so verbatim and requests a catalog rebuild), yet the rebuild is sliced across frames with the stale `visible_` list still clickable, and is *explicitly deferred for as long as the editor is open* (VideoLibraryMenu.cpp 5810–5816) while every editor action calls `Describe(selected_)`. Trigger: a SongCore refresh while the editor is open (the project's own ShowcaseLauncher triggers one; background map-installer mods can too), then GC, then any editor interaction. Consequence: garbage strings or SIGSEGV. Whether Boehm actually collects inside the window is timing-dependent — hence Risk, not confirmed defect. Fix: on `RequestCatalogRefresh`, immediately clear `visible_`, and re-resolve `selected_` by `levelId` through SongCore on next use instead of trusting the pointer. Confidence: Medium.

### M-14 — Per-frame managed-string material updates in the GPU YUV upload path
Every uploaded GPU frame calls `ConfigureGpuConversionMaterial` (invoked at ScreenSurface.cpp 2222 and 2290) issuing ~17 `SetVector/SetFloat("name", …)` plus two `SetTexture("_PlaneU"/"_PlaneV")` (2220–2221) — each `const char*` converts to a managed `System.String` allocation, ~1,100 allocations/sec at 60 FPS on the hottest path in the mod, recomputing a color matrix that effectively never changes mid-session. Fix: cache `Shader::PropertyToID` ints once per material and skip re-upload unless the relevant frame fields changed. Confidence: High that the code does this; Medium on user-visible impact (GC pressure is the classic Quest frame-spike source, but no measurement exists either way).

### M-15 — The one shipped binary restored by QPM is not hash-pinned
Every other external input (NDK, QPM CLI, FFmpeg, x264, CPython, yt-dlp, certifi, QuickJS, schema) is SHA-256-pinned, and the docs advertise byte-identical reproducible QMODs — but `libbeatsaber-hook.so` and the other link-time `.so`s from `qpm.shared.json` `soLink` release URLs are verified by version only; `bootstrap-linux.sh` records a lockfile-hash cache stamp, not artifact digests. A re-uploaded release asset changes shipped bytes and breaks the reproducibility claim silently. Fix: record expected SHA-256s for restored `extern/libs/*.so` (at minimum the packaged `libbeatsaber-hook.so`) and verify after `qpm restore`. Confidence: Medium (depends on the mutability of those GitHub release assets, which was not tested — see Section 8).

## 7. Low-Severity Findings

All verified at the cited lines; each entry gives location → problem → smallest fix. Confidence High unless noted.

1. **Probe script lacks network bounds** — DownloadManager.cpp 1381–1391: the URL-probe `YoutubeDL` options omit the `socket_timeout: 15 / retries: 3 / extractor_retries: 3` the transfer options carry with an explicit Quest rationale (828–834). A flaky network holds the single serialized operation queue for minutes. Fix: copy the three bounds.
2. **Probe failures count as "YouTube downloads failed"** — DownloadManager.cpp 4199/4212 → `RecordYouTubeDownloadOutcome` (2281–2328): three failed URL *checks* (dead mapper URLs) trigger the "Several YouTube downloads failed" notice and a release check; successful probes never reset the streak (only `Completed` does). Fix: exclude probes or reset on probe success.
3. **Misleading composite failure text** — VideoContainerNormalizer.cpp 539–556: when the software probe never ran (non-MPEG-TS or >1080p short-circuit), the terminal diagnostic still appends "Software validation also failed: " followed by an empty string, sending support triage after a phantom decode attempt. Fix: append the clause only when the probe was attempted.
4. **Diagnostic-throttle state reset only by `Start()`** — DownloadManager.cpp 2411 is the only reset of `lastDiagnosticState_`/progress bucket; `StartMapPackage`/`StartProbe`/`StartUpdaterCheck` inherit the prior operation's values, so their first `download_stage` transition can be suppressed or mislabeled in diagnostics. Fix: hoist the reset into `QueueOperation`.
5. **`UpdateGeometry` rollback leaves deformation caches describing the new geometry** — ScreenSurface.cpp 1637–1650 restores `previousVideoMesh` after an `ApplyPresentation` failure, but `CreateVideoMesh` already overwrote `deformationBaseVertices_`/`dynamicVideoVertices_`/UV arrays (1585–1595), possibly with a different vertex count; a later `SetDeformation` would corrupt the restored mesh. Reachability is narrow (showcase-only, requires a transient shader failure coinciding with a letterbox/opacity delta). Fix: snapshot/restore or clear the five arrays in the rollback.
6. **`MatchesCinemaScreen` "Exact" lookup is not exact** — ChromaMapDetector.cpp 404–405: the suffix branch accepts any id merely *ending* in `CinemaScreen` (e.g. a mapper's own `MyCinemaScreen`), hijacking its transforms for the menu preview. Fix: require `'/'` before the suffix.
7. **Cinema clone lights never unregistered** — CinemaEnvironment.cpp 121–142 registers clone lights with `LightWithIdManager`; `Cleanup()` (145–170) destroys clones without `UnregisterLight`. Between the compatibility-cycle's mid-scene phases (PlaybackSession.cpp 1044) the manager dispatches lighting events into destroyed components for the rest of the map; ordinary maps are exposed only for the brief Stop→scene-unload window. Fix: unregister in `Cleanup` before `Destroy`.
8. **Dead `SetDiagnosticsText`** — ScreenSurface.cpp 3281–3326 has no callers anywhere (grep), uses raw-pointer guards unlike the rest of the file, and would call `set_text` on a fake-null object after teardown. Fix: delete it (or align guards if it is about to gain a caller).
9. **Bloom-state normalization contradictions** (compiled-out surface) — `Destroy()` resets `mapperBloom_ = 1.0f` (3211) while the disabled-experiment branch of `CreateInternal` uses `0.0f` as neutral (1267); `bloomRegistered_ = false` is set both inside the `#if` (3207) and unconditionally (3210). Cosmetic today; a trap if the experiment returns. Also: duplicate `#include <string>` (ScreenSurface.hpp 12 and 21) and `Upload` re-setting `set_mainTexture` immediately after `ApplyPresentation` already did (2118).
10. **Copy-pasted timing-load block, 4 copies, drifted** — VideoLibraryMenu.cpp 2946–2967, 3422–3444, 3924–3945, 4198–4216: near-identical "Describe → populate editor fields under suppressed callbacks" blocks; the `SaveTiming` restore variant omits the `url_`/`mapperProvidedUrl_` refresh. Fix: one `ApplyDescriptorToEditor` helper.

## 9. Threading, Ownership, and Lifetime Assessment

Thread inventory (verified against creation/join sites):

| Thread | Created | Owner | Shutdown | Joined |
|---|---|---|---|---|
| `BigScreenDecode` (FrameDecoder worker, per open decoder, per backend) | `FrameDecoder::Open` | the decoder instance | `stopWorker_` published under `requestMutex_` + CV notify; FFmpeg I/O interrupted via callback + 1 s open deadline | `Close()` joins; facade gives Unity a 4 ms budget (`WaitForWorkerStop`) then hands the backend to the reaper |
| `BigScreenReap` (decoder retirement) | first retirement, detached | process-lifetime singleton (deliberate leak-by-design, documented rationale: Quest never unloads native mods; avoids static-destruction ordering) | none (intentional) | never (intentional) |
| `BigScreenDL` operation worker + status poller (100 ms) | `DownloadManager::Initialize` | DownloadManager singleton | stop flags + CVs | destructor joins |
| mod/yt-dlp release workers (per check) | on demand | DownloadManager | run-to-completion; `*Finished_` flag is the lambda's final `this` touch; next start detaches only after observing the flag; destructor joins any joinable handle | yes |
| thumbnail worker (lazy) | `QueueVideoThumbnail` | DownloadManager | stop flag + CV | destructor joins |
| Catalog sort worker | VideoLibraryMenu | menu | generation-guarded publish; operates only on native string copies | joined before restart |
| Local-video scan worker | LocalVideoBrowserMenu | menu | atomic stop + request generation | joined before restart |
| NativeLogger writer | logger init | logger singleton | CV + `writer.join()` | yes |

Unity-thread discipline: every Unity/IL2CPP touchpoint I traced originates from main-thread hooks; background workers publish through mutex-guarded snapshots polled on the Unity thread (download status mailbox, decoder frame mailbox, scan snapshots, ErrorManager pending-dialog + `TickMainThread`). I found **no** background-thread Unity call, including through callbacks. Cross-thread handoffs carry generation/epoch stamps so late results are rejected rather than raced.

Lock discipline: CV predicates are consistently mutated under their predicate mutexes with in-code explanations of the lost-wakeup hazard (FrameDecoder.cpp 683–701, 1048–1055 — textbook). No lock-order inversion was found: the only nesting in DownloadManager is `statusReadMutex_ → mutex_` with no reverse path; FrameDecoder's `requestMutex_`/`outputMutex_` are taken sequentially, never nested in reverse. No callback or file I/O under the public `mutex_`. Joins never occur while holding a mutex the worker needs.

Weakest lifetime areas, in order: the raw `BeatmapLevel*` catalog pointers (M-13); the raw-vs-`isAlive` guard split inside ScreenSurface (M-5, M-4); the unverified multiplayer/tutorial ownership boundary (Section 8.1). Strongest: the decoder stack end to end, and the ownership bit + destruction ordering for shared textures (clones always destroyed before the texture owner — verified at PlaybackSession.cpp 1893–1895 and in the cycle path).

## 10. Error-Handling Consistency

The codebase has an explicit, layered philosophy and mostly follows it: recoverable low-level operations return bool/status with `error` out-params; feature failures degrade the feature and continue the map (additional Cinema panels, showcase panels, thumbnails are all "never cost the player a map" — verified at their call sites); persistent user-visible failures go through `ErrorManager::ReportUserVisible` with dialogs deferred past gameplay; expected/environmental failures are recorded via `RecordError` (documented at ErrorManager.hpp 30–31 as *not* counting toward the breaker); unexpected internal failures use `ReportInternal` feeding a 2-in-3-minutes circuit breaker that self-disables the mod; native-invalid-state risk is handled by prevention (`isAlive` + epoch/generation guards), not try/catch; every hook body is wrapped in `ErrorManager::Guard` as the final noexcept boundary. Worker errors travel by mailbox (`TakeError`) to the main thread.

Verified inconsistencies against that philosophy: H-2 (manifest write failure routed to `ReportInternal` where the equivalent settings failure correctly uses `ReportUserVisible` — the one place an expected environmental failure can trip the breaker); M-3 (two sanitizers of different strength, with the weaker one feeding the persistent log and a comment claiming otherwise); M-2 (a recovery path keyed to a condition that cannot represent the failure it targets); Low-3 (a composite error message asserting a validation step ran when it did not). Diagnostic quality is otherwise a strength: stable error codes (`BS-DL-…`), correlation IDs linking error-history to session logs, subsystem/operation/context in nearly every message.

## 11. Decoder and Media Pipeline Assessment

Read in full and traced end to end (select → prepare → demux → codec policy → HW/SW decode → timing normalization → conversion → mailbox → upload → sync → pause/seek/replay/restart → EOF → teardown). This is the strongest subsystem in the repository:

- The send/receive packet contract handles the EAGAIN-means-not-consumed rule correctly and documents the prior bug it fixes (1452–1481); drain is bounded (250 ms) and EOF is latched as a codec state with correct backward-seek invalidation; NOPTS timestamps are preserved as NaN and normalized centrally rather than collapsed to zero; crop metadata is applied before swscale (MediaCodec stride bars); colorspace/range are applied uniformly across HW/SW so fallback does not shift colors; rotation is applied once from the display matrix with user rotation kept as a separate UV transform.
- Synchronization: Beat Saber song time is the only clock everywhere I looked — pause, practice speed, Replay, restart, scrub all arrive as externally-supplied timestamps; the presentation-slot quantization limits request rate without altering decode targets; clock discontinuities rebase measurement epochs rather than corrupting miss statistics; the GPU read-ahead's expected lead is explicitly excluded from rewind detection. No wall-clock or frame-count timing crept in.
- Failure behavior: hardware failure mid-stream reopens the same file in software at the current position, preserving one-way GPU-fallback decisions (`ReopenWithSoftwareAfterHardwareFailure`); HEVC/>1080p software fallback is correctly refused with the blocked reason surfaced; a parseable container with zero decodable frames is treated as media failure, not EOF; worker errors close the decoder promptly and release memory mid-map.
- Memory: bounded frame pool keyed to the byte budget with a 120-frame ceiling, buffers recycled across restarts, GPU/CPU pools never held simultaneously (explicit swap-release on the one-way transitions).

Residual items are all at the edges: M-4/M-5 (surface guard/commit ordering), M-14 (per-frame material strings), the facade's `Upload`-size-mismatch conflation (latent: output dimensions are fixed at open today, but a future resize would be misdiagnosed as "screen destroyed" — ScreenSurface.cpp 2096–2102 + PlaybackSession.cpp 1753–1767), and the D1 input-side splice risk. The 4 ms teardown budget plus retirement reaper is a deliberate, well-documented tradeoff (a hung MediaCodec must not stall UnityMain), and the reaper's process-lifetime detachment is safe because retired backends are fully self-contained.

## 12. Rendering / Unity Lifecycle Assessment

Ownership is disciplined and verified: `ownsTexture_` is exactly `sharedTexture == nullptr`; `Destroy()` destroys owned textures/RT/materials/meshes and only nulls clone pointers; every `CreateInternal` failure branch funnels through `Destroy()`; showcase/cinema groups destroy all panels on partial failure and never touch the shared texture; geometry replacement is publish-after-success with the old mesh destroyed last (the M-4/M-5 ordering slips and the Low-5 rollback residue are the exceptions that prove the rule). No leak across repeated songs/restarts was found: both restart controllers and the StartSong re-entry path call `Stop()`, and `Stop()` orders Unity destruction before decoder close with the reasoning in comments. Per-frame work does not scale with screen count (one decode + one upload; clones share the texture; visibility/opacity setters early-out on unchanged state). Geometry/UV/color math was checked independently (curvature arc-length scaling, V-inversion convention across all four vertex producers, Sutherland–Hodgman clipping, BT.601/709/2020 matrices and limited-range factors): consistent and correct. The compiled-out bloom experiment is cleanly gated and honestly labeled.

## 13. Downloader / Embedded Runtime Assessment

The Python/GIL discipline is textbook (single main-thread `Py_InitializeFromConfig`, `PyEval_SaveThread` on every init exit path, RAII GIL scopes for workers, GIL released around QuickJS CPU work, borrowed refs copied inside the GIL scope, exception text retrieval that clears secondary errors). The status protocol (Python: tmp+fsync+`os.replace`; C++: never parse partial JSON, never hold the public mutex across I/O) and the `SetFailure`/`ignoreStatusFile_` resurrection guard are airtight — I attempted to break both and could not. The updater chain (SHA-256 against official sums, size caps on declared and streamed bytes, zip testing, staged activation with rollback and a rejected-version memory, and a startup smoke test that executes the EJS solver before accepting a package) and the BeatSaver map-install hardening (host allowlist re-verified post-redirect, entry/size caps, symlink rejection, realpath containment for both archive entries and Info.dat-declared files) are genuinely strong. QuickJS runs per-call with memory/time/output caps. Thumbnails never trust metadata URLs (locally validated 11-char ID pinned to `i.ytimg.com`, 4 MB cap). The URL gate is https-only with proper suffix matching.

Defects are concentrated in the seams: H-1 (partial-file identity), M-2 (dead rollback), M-3 (sanitizer split), Lows 1–4. The yt-dlp compatibility paths (client-selection workaround, 403 retry-from-zero, HLS fallback) are dated, explained, and non-contradictory — deliberate compatibility engineering, not slop.

## 14. Filesystem / Deployment / Removal Safety

First-party file operations are conservative and were individually checked: every recursive deletion root in the removal scripts is a compile-time constant re-checked by equality before use; receipt-driven removal is per-file `rm -f -- '<path>'` with directory pruning restricted to empty directories; `libbeatsaber-hook.so` and all non-BigScreen libraries are classified `SharedDependency` and can never reach `rm`; MBF-managed installs are detected and refused for both deploy and remove; remote paths pass an injection filter (prefix + no quotes/CR/LF/`..`) before interpolation, including paths derived from a hostile MBF manifest; deploys are gated on a hash-verified build stamp; the deterministic-zip tool rejects traversal entries and the QMOD's entry set is re-verified against the manifest; third-party archives are extracted entry-by-entry under caps, never `extractall`. In-app, download staging is transactional (`StagedFileReplacement` promote/commit/restore with leftover-backup recovery) and `CommitDownload` deletes only differently-named managed files after a successful save.

The confirmed weaknesses are parity, not principle: M-8 (Linux deploy lacks the ownership assertions and baseline restoration the PS path enforces — the one place a user file can be silently clobbered), M-11 (the ownership logic's tests run nowhere), and the Low-13/14 developer-script items. ## 22. Potential Issues Investigated and Rejected

Each rejection was confirmed by the lead reviewer at the cited code.

- **`outtmpl`/path injection via song or video titles — REJECTED.** Download and thumbnail paths are built exclusively from `<16-hex-FNV(StableVideoKey)>-{user|mapper}.{ext}` under a constant root (VideoLibrary.cpp 909–926); no remote-controlled character reaches a filesystem name; titles live only inside JSON values.
- **Detached release-worker use-after-free — REJECTED.** The `*Finished_` flag is the lambda's final `this`-touching statement; the next start detaches only after observing it true; the destructor joins any still-joinable handle. No window exists.
- **FrameDecoder worker lifetime/lost-wakeup — REJECTED.** Stop flag is published under the predicate mutex before notify; `Close()` joins before freeing FFmpeg state; in-flight conversions are rejected by decode epoch at `Publish`. The retirement path never frees state a worker can still touch (the whole backend moves).
- **Status-file resurrection after a C++-side failure — REJECTED.** `SetFailure` publishes `ignoreStatusFile_` under `mutex_` before truncating; `RefreshSnapshotFromDisk` re-checks flag+path under the same mutex before writing back.
- **Lock-order inversions in DownloadManager / FrameDecoder — REJECTED.** Single-direction nesting only (`statusReadMutex_→mutex_`; request/output mutexes sequential).
- **Missed-Stop leak on restart — REJECTED.** Both restart controllers and the StartSong re-entry branch call `Stop()` before the new session (main.cpp 1559–1604, 1685–1697).
- **`StagedFileReplacement` destroying known-good video on failed replacement — REJECTED.** Promote/commit/restore ordering plus leftover-backup recovery is transactional; `CommitDownload` deletes only differently-named managed files after a successful save.
- **Mesh division-by-zero via `screenSegments` — REJECTED.** Clamped to 1..256 at parse (MapVideoConfig.cpp 359–362).
- **Fracture impact-array overflow — REJECTED.** Count clamped against both source and cache capacities; cache type aliased to the public settings type so they cannot diverge.
- **Thumbnail request spam per UI tick — REJECTED.** Per-destination session dedupe in `QueueVideoThumbnail`.
- **Local-browser scan-thread races — REJECTED.** Atomic stop, request-generation-guarded publish, join before restart.
- **Python `classify()` operator-precedence bug — REJECTED.** `and`-over-`or` precedence yields the intended grouping.
- **CV-predicate races in NativeLogger — REJECTED** (verified by its concurrency test and source).
- **`qpm_defines.cmake`'s broken non-fatal NDK error — REJECTED as unused.** The file is not included by the build; `cmake/targets/android-ndk.cmake` implements the real, fatal check.
- **CI hang on the interactive bootstrap prompt — REJECTED.** The prompt helper fails fast on non-TTY stdin, and the workflow pre-installs packages so the prompt path is not reached.
- **Committed build artifacts (`Big Screen.qmod`, `CMakeCache.txt`, root `mod.json`) polluting the repository — REJECTED.** All confirmed gitignored; CI regenerates `mod.json` before tests read it.
- **`ShowLeadIn(false)` (transparent lead-in) sharing M-4's defect — REJECTED.** That branch sets state before any fallible operation.
- **`UploadRgba` recreating its texture without rebinding the material — REJECTED.** The reachable-case analysis shows the bound texture is either alive or the upload is rejected earlier.
